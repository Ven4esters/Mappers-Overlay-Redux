# ADR-0053. Выпуск одной командой, вложения — из CI, подпись SBOM — sigstore

- Статус: принято; уточняет [ADR-0046](0046-releases-with-assets-only.md) и
  [ADR-0047](0047-exe-release-checksums.md)
- Дата: 2026-11-19
- Владелец: @Ven4esters
- Пересмотр: 2028-11-19
- Версия: 1.27.0

## Контекст

Пункты 20 и 23 плана. Выпуск 1.24–1.26 собирался руками: номер версии поднимался в четырёх
местах (`map_overlay/__init__.py`, `pyproject.toml`, строка «Версия — X.Y.Z» и бейдж в README),
CHANGELOG дописывался отдельно, скриншоты пересобирались «если вспомнили», проверки гонялись
на доверии, тег ставился после. Забытый бейдж видно только на странице проекта, а расхождение
версии с тегом — только тем, кто ставит пакет из тега.

Вложения релиза при этом оставались проблемой: `ADR-0046` запретил публиковать релиз без файлов,
потому что среда разработки не может загружать вложения (`uploads.github.com` недоступен), а
`ADR-0047` разрешил прикладывать файлы, собранные на машине сопровождающего. Практика показала:
разрешённый ручной путь не выполняется — у тегов 1.24.0–1.26.0 релизов нет вовсе.

Пункт 23 добавляет второе требование: у скачавшего должна быть возможность проверить, что файлы
не подменены, а состав зависимостей — подписан. Сертификат подписи кода (SmartScreen) стоит денег
и требует юридического лица; это отдельный, более долгий путь.

## Варианты

1. **Оставить ручной выпуск и добавить чек-лист в DEVELOPMENT.** Самый дешёвый вариант, но
   чек-лист уже был — в виде «порядка заполнения» в DEVELOPMENT.md, и он не соблюдался. Отвергнуто:
   повторять инструкцию, которую не выполняют, бессмысленно.
2. **Подписывать всё долгоживущим ключом (GPG или собственный).** Ключ надо хранить в секретах,
   передавать его пользователям, ротировать при утечке и объяснять, как импортировать. Для
   проекта, где подписывающий — один человек, а проверяющих — сотни, это дороже, чем даёт.
3. **Собирать вложения на машине и загружать `gh release upload`.** Работает, но требует Windows-
   машины с PyInstaller, сети до `uploads.github.com` и памяти о том, что этот шаг есть. Отвергнуто
   по той же причине, что и вариант 1, плюс: файлы, собранные не в CI, невозможно воспроизвести.
4. **Выпуск одной командой + воркфлоу по тегу + подпись sigstore без ключей (выбрано).**
   `python -m tools.release X.Y.Z --push` поднимает версию везде, где она живёт, пересобирает
   картинки и таблицу формул, гоняет проверки CI, коммитит и ставит аннотированный тег. По тегу
   воркфлоу собирает zip исходников, колесо, SBOM, подписывает SBOM через sigstore (эфемерный
   ключ из OIDC-токена прогона), считает `SHA256SUMS.txt` и создаёт релиз.

## Решение

**Версия.** Один список мест (`tools/release.py: PLACES`) — единственный источник правды о том,
где живёт номер. `--check` сверяет все места между собой и (если передан) с тегом; эту проверку
выполняет job «Документация» в CI, поэтому релиз с разными номерами не пройдёт.

**Текст изменений.** Раздел `## [X.Y.Z]` в CHANGELOG пишет человек: команда не выдумывает заметки.
Нет раздела — выпуск не начинается и файлы не меняются. Сообщение тега — этот же раздел, поэтому
страница тега и страница релиза говорят одно и то же.

**Проверки.** Перед коммитом гоняются те же проверки, что в CI (`check_docs`, `check_exceptions`,
`ruff`, `mypy`, `pytest`). Картинки и таблица формул пересобираются только по флагу `--images`:
golden-тест и `check_docs` уже падают на устаревших, а безусловная пересборка на другой машине
приносит разницу растеризатора вместо изменений интерфейса — и выпуск начинает трогать файлы,
которых никто не менял.

**Вложения.** Собираются только в CI по тегу. Отсюда следует, что релиз не может содержать файлов,
которых нет в истории: `git archive` берёт их по списку из git, колесо собирается из тега, SBOM —
из окружения того же прогона.

**Подпись.** SBOM подписывается sigstore в режиме keyless: ключевая пара живёт минуты, сертификат
привязан к воркфлоу и тегу, подпись и сертификат лежат в `sbom.json.sigstore`. Проверка на стороне
пользователя — `sigstore verify github --repository … --ref refs/tags/vX.Y.Z`; ни секретов, ни
нашей инфраструктуры для этого не нужно, доверие идёт к прозрачному журналу Sigstore.

**Границы.** Подпись кода для `.exe` (SmartScreen) этим решением не закрывается — она требует
сертификата и остаётся отдельной задачей. `.exe` в релиз пока не вкладывается; в релизе лежат
исходники, колесо, SBOM, подпись и суммы.

## Результат

Первым же прогоном по тегу `v1.27.0` воркфлоу создал релиз с архивом исходников, колесом, SBOM,
подписью (`sbom.json.sigstore`) и `SHA256SUMS.txt`; шаг «SBOM и подпись» включает проверку подписи
через `sigstore verify github`, поэтому подпись подтверждена до публикации. Прогон занимает 23 с.

## Последствия

- Релизы появляются автоматически на каждый тег: `gh release list` перестаёт быть пустым, а
  README ведёт в Releases.
- Числа для проверки скачанного (`SHA256SUMS.txt`) и подпись SBOM существуют с первого же релиза —
  вручную их никто не набирает.
- Человек в выпуске решает ровно одну задачу: что написать в CHANGELOG.
- Пробный прогон (`workflow_dispatch`) собирает файлы, но релиз не публикует: настройку воркфлоу
  можно проверить, не занимая номер версии.
- Откат: убрать шаг `tools.release --check` из CI и воркфлоу `release.yml` — выпуск снова станет
  ручным, а вложения — отсутствующими (как до 1.27.0).
- Затронуты: `tools/release.py`, `.github/workflows/release.yml`, `tests/test_release.py`,
  `README.md`, `docs/DEVELOPMENT.md`, `.github/workflows/ci.yml`, `CHANGELOG.md`,
  `docs/adr/0046-releases-with-assets-only.md`, `docs/adr/0047-exe-release-checksums.md`.
