# ADR-0030. Полное логирование действий и журнал последних событий

- Статус: принято
- Дата: 2026-11-19
- Владелец: @Ven4esters
- Пересмотр: 2027-11-19
- Версия: 1.10.2

## Контекст

Заказчик попросил «полное логирование действий, чтобы выяснить, из-за чего возникают
зависания». Смотреть было нечего:

- файл `overlay.log` по умолчанию писал только уровень INFO: подробные строки панели
  («читаю поле X», «пишу поле Y») появлялись лишь с флагом `--debug`, то есть в реальной
  работе отсутствовали;
- в журнале не было длительности операций: строка «Читаю поле X» ничего не говорит о том,
  что дальше не вернулось;
- нажатия клавиш и решения («пропущено: занято», «съедено заморозкой») в журнал не
  попадали вовсе — а именно они объясняют, почему оверлей «не реагирует»;
- сторож зависаний писал стеки потоков, но не писал, **что оверлей делал** до остановки:
  стек показывает `WaitForSingleObject`, а не «на каком поле всё встало»;
- короткие подвисания (1–3 с) не замечались вообще: сторож реагировал только с 8 с.

## Решение

### 1. Файл журнала всегда пишет DEBUG

`setup_logging` держит корневой уровень DEBUG, файловый обработчик — DEBUG; объём ограничен
существующим поворотом (2 МиБ × 3). Консоль по умолчанию пишет с INFO, а с `--debug` — тоже
DEBUG. Раньше «подробно» означало «флаг в командной строке», и заказчик его не ставил.

### 2. Журнал действий (`map_overlay/trace.py`)

Единая функция `note()` пишет строку в логгер `map_overlay.action` (DEBUG, то есть в файл) и
в кольцевой журнал `JOURNAL` — последние 150 событий в памяти с временем, смещением и именем
потока. Пишутся:

- каждая клавиша от хука и решение по ней: нажата/отпущена, автоповтор, «съедена
  заморозкой», «забрана у игры», «пропущена: перехват выключен», «→ команда «…»»;
- команды интерфейса: «считать», «сохранить F», шаг, «Прервать», дедлайн, удержание,
  режим высоты, назначение клавиши;
- занятость: «начато действие», «занятость: включена/снята»;
- задачи: постановка, запуск потока, завершение/провал/бросок с длительностью;
- панель: клик с точкой, чтение и запись поля со значением, ожидание отпускания
  `Alt`/`Ctrl`/`Shift` с длительностью;
- шаг: поза «до» и «после», какие поля пишутся, сверка панели, результат проверки записи;
- каждый статус в строке состояния.

### 3. Пары «начал/готово» и порог медленной операции

Контекстный менеджер `timed()` пишет «начал: <операция>» и «готово: … — N мс». Операция
дольше 1200 мс пишется предупреждением `Медленная операция`. Главное следствие: **«начал»
без «готово» — и есть место зависания.** Именно этой пары не хватало: теперь видно, что
обмен встал, скажем, на чтении поля `Y`, а не «где-то в панели».

### 4. Сторож зависаний получает журнал действий

- Подвисание дольше **2.5 с** — предупреждение в журнал с последними действиями (стеки не
  снимаем: это ещё не зависание, а его начало).
- Зависание дольше **8 с** — `crash.log` и `logger.critical` получают отчёт: сначала
  «Последние действия оверлея» (150 строк), затем стеки всех потоков. Критическая ошибка и
  падение в потоке тоже дописывают последние действия.
- Восстановление после зависания пишется в `crash.log` с длительностью паузы.

### 5. Строка «жив» каждые 20 секунд

Периодическая сводка: занятость и её длительность, шаг, удержание, режим высоты, координаты.
Даже если сторож ничего не успел, в журнале будет последний снимок состояния.

## Последствия

- `overlay.log` заметно подробнее; объём ограничен поворотом (до 8 МиБ на диске).
- В журнале видны значения полей панели и координаты: это не секреты, но файл стоит
  просматривать перед публикацией.
- Подробность не влияет на скорость: `note()` — это строка в буфер логгера и запись в
  `deque` под коротким мьютексом.
- `--debug` теперь управляет только консольным выводом, а не подробностью файла.
- Тесты: `tests/test_trace.py` (журнал, пары «начал/готово», медленные операции),
  расширенные `test_logging`, `test_diagnostics`, `test_panel`, `test_ui` — всего 907.

## Что делать с этими данными

1. Найти в `crash.log` блок «Последние действия оверлея».
2. Найти последнюю строку «начал: …» без парной «готово: …» — это и есть зависшая операция.
3. Сопоставить её со стеком того потока, где она выполнялась (стек идёт сразу ниже).
4. Проверить в `overlay.log` предупреждения «Медленная операция» и «Интерфейс не отвечает»:
   они показывают, на каких полях тормозит панель и с какого момента началось.

## Альтернативы

- **Включить DEBUG только по флагу.** Уже было: заказчик флаг не ставит, а после зависания
  перезапускает приложение — данные теряются.
- **Писать подробности в отдельный «журнал действий».** Пришлось бы синхронизировать два
  файла по времени; одна строка JSON с общим `time` проще.
- **Хранить журнал действий в файле.** Тогда он не переживёт подвисание диска/записи, а в
  памяти 150 событий стоят копейки.
