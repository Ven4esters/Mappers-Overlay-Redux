# ADR-0048. Один экземпляр оверлея: именованный мьютекс Windows

- Статус: принято
- Дата: 2026-11-19
- Владелец: @Ven4esters
- Пересмотр: 2027-11-19
- Версия: 1.24.0

## Контекст

Оверлей ставит глобальный хук клавиатуры. Запустили его дважды — хук ставят оба экземпляра, и
каждая клавиша приходит дважды: шаг выполняется два раза, история шагов заполняется парами, а
координаты уезжают на двойное расстояние. Со стороны это выглядит как «оверлей сошёл с ума»:
два окна, оба выглядят рабочими, в журнале каждая клавиша записана дважды с разными процессами.

Пункт 3 [плана улучшений](../IMPROVEMENT-PLAN.md) требует: второй экземпляр показывает сообщение
и выходит с кодом 2. Пункт 4 того же плана добавляет второе требование — в `--check-only` должна
быть строка о занятости замка, иначе пользователь не понимает, почему «не запускается».

## Рассмотренные варианты

1. **Ничего не делать.** Два экземпляра — двойные шаги; диагностика упирается в «в журнале всё
   правильно», потому что каждая строка действительно правильная, просто их две.
2. **Файл-замок.** Просто и переносимо, но при падении процесса файл остаётся лежать. Оверлей
   снимают через диспетчер задач регулярно, так что пользователь получал бы «запуск невозможен»
   без видимой причины и без способа починить — это хуже исходной проблемы.
3. **Именованный мьютекс Windows** (выбрано). Замок снимается системой при завершении процесса,
   в том числе аварийном: чистить нечего. Имя `Local\MappersOverlayRedux.SingleInstance` —
   на сеанс пользователя, поэтому два пользователя на одной машине друг другу не мешают.
4. **`QSharedMemory`.** Тоже вариант, но создаёт раздел памяти, который тоже надо не забыть
   освободить, и на Linux ведёт себя иначе, чем на Windows. Мьютекс — ровно то, для чего он есть.

## Решение

Замок берётся **до** создания `QApplication` и до установки хука: `InstanceLock.acquire()` в
`map_overlay/main.py::_run_window`. Если имя занято — печатается строка в `stderr`, показывается
сообщение и возвращается код 2; `QApplication` создаётся только для этого сообщения.

Создание и закрытие мьютекса вынесены в две функции (`_create_mutex`, `_close_mutex`) и передаются
в конструктор `InstanceLock`. Причина: на Linux (тесты, проверка документации) мьютексов нет, и
подменять две функции проще, чем поднимать Windows. Если мьютекс создать нельзя, запуск **не
блокируется**: лучше два экземпляра, чем ни одного — отказ в запуске из-за непроверяемой проверки
недопустим.

В `--check-only` пробный захват тут же отпускается: строка «Экземпляр: уже запущен — второй не
стартует» объясняет поведение, ничего не ломая.

Граница применимости: **окно первого экземпляра не поднимается**. Для этого нужен канал между
процессами (`QLocalServer`/именованный канал), а сообщение «уже запущен» решает задачу «почему не
открывается» без него. Если появится требование «второй клик по ярлыку поднимает окно» — это
отдельная работа, и она не меняет решение о замке.

## Последствия

- Двойные шаги из-за двух запусков невозможны; причина «не запускается» видна и в сообщении, и в
  `--check-only`.
- Замок не оставляет мусора: снимается при выходе, при падении, при снятии процесса.
- На Linux и в тестах проверка отключена штатно, а не «по случайности»: `_create_mutex` возвращает
  «недоступно», и это записано в журнал на уровне DEBUG.
- Затронуты: `map_overlay/infrastructure/single_instance.py`, `map_overlay/main.py`, `README.md`,
  `tests/test_single_instance.py`, `tests/test_cli.py`.
- Откат: убрать вызов `InstanceLock` из `_run_window`; файл `single_instance.py` при этом можно
  оставить — он ни на что не влияет, пока его не вызывают.
