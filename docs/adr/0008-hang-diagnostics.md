# ADR-0008: диагностика зависаний

## Контекст

После серии нажатий оверлей перестал отвечать, процесс пришлось завершать аварийно.
В журнале не было ни ошибки, ни незавершённой записи: писались только успешные шаги,
а исключения интерфейса уходили в stderr, которого у окна нет. Причины не видно —
значит, виноват не код приложения, а отсутствие наблюдения.

Известные пути к «зависанию»:

1. задача в фоне встала (буфер обмена, панель, SendInput) — окно занято навсегда;
2. исключение в обработчике результата — признак занятости не снимается;
3. поток интерфейса реально замер (мёртвая блокировка Qt или вызов Win32).

## Решение

1. **Пишем не только успех.** Каждая задача: «начата», «выполнена за N с» или «не выполнена
   за N с: причина». Отдельные операции панели — в режиме `--debug`.
2. **Ловим всё, что раньше уходило в stderr:** `sys.excepthook`, `threading.excepthook`,
   плюс `faulthandler` для fatal error. Файл — `logs/crash.log`, чтобы JSON-журнал оставался
   машинно-читаемым.
3. **Сторож сердцебиения.** Поток интерфейса каждые 250 мс отмечает `beat()`. Отдельный
   поток-сторож при паузе больше 8 секунд пишет стеки всех потоков (`sys._current_frames`)
   в журнал и `crash.log`, а когда интерфейс оживает — пишет об этом.
4. **Окно не остаётся «занятым».** Занятость снимается до обработки результата; исключение
   обработчика логируется. Кнопка «Прервать» бросает задачу: её номер увеличивается,
   поздний результат игнорируется.
5. **Поток задачи останавливает себя сам** — не зависит от того, успел ли интерфейс
   обработать сигнал.

## Последствия

- Диагностика не имеет права мешать работе: все её вызовы внутри `try/except`.
- Сторож — единственный постоянный фоновый поток приложения; он спит по секунде.
- Если зависание повторится, в `crash.log` будет стек виновника; без него любая правка —
  догадка.
