# ADR-0046. GitHub Releases — только вместе с вложениями, собранными в CI

- Статус: принято; в части «вложения только из CI» уточнено [ADR-0047](0047-exe-release-checksums.md)
- Дата: 2026-11-19
- Владелец: @Ven4esters
- Пересмотр: 2027-11-19
- Версия: 1.23.4

## Контекст

К версии 1.23.2 в репозитории было 23 тега и **ни одного** GitHub Release: `gh release list`
возвращал пустой список, `GET /releases` — `[]`. Единицей поставки служил тег: архив
`Mappers_Overlay_Redux_vX.Y.Z.zip` собирался локально по `git ls-files`, README предлагал
«скачать папку проекта целиком (или клонировать репозиторий)».

При выпуске 1.23.2 релиз был создан с описанием, но без файлов: среда разработки не может загружать
вложения. Проверка хостов это подтвердила — `github.com`, `api.github.com` и `codeload.github.com`
отвечают, а `uploads.github.com` (он же `alambic-origin.githubusercontent.com` из шлюза выхода),
`objects.githubusercontent.com` и `raw.githubusercontent.com` рвут TLS-рукопожатие. Первый же
`POST` на `uploads.github.com` вернул `EOF`, и релиз остался без `Mappers_Overlay_Redux_v1.23.2.zip`,
без `sbom.json` и без `SHA256SUMS.txt`.

Отсюда вопрос: что даёт пользователю релиз, в котором нет ничего, кроме текста?

## Рассмотренные варианты

1. **Оставить релизы без вложений** (так и было сделано для 1.23.2 и 1.23.3). Плюс: раздел
   Releases перестаёт быть пустым, у последнего тега появляется человекочитаемое описание. Минусы:
   описание дублирует CHANGELOG, а главное — страница релиза обещает сборку, которой нет. Исходники
   любого тега GitHub и так отдаёт через «Source code (zip)» и «Source code (tar.gz)», так что
   сверх тега такой релиз не добавляет ничего.
2. **Собирать вложения вручную на своей машине и прикладывать их к релизу.** Технически возможно
   (`gh release upload`), но это ручной шаг, который забывается: ровно та же болезнь, из-за которой
   релизы не создавались вовсе.
3. **Не публиковать релизы, пока вложения не собирает CI** (выбрано). Ветка «тег → воркфлоу →
   zip, SBOM, SHA256SUMS, релиз» появляется один раз и дальше работает без человека.
4. **«Ничего не делать»** — то же, что вариант 1, только без решения: следующий выпуск снова
   упрётся в тот же вопрос.

## Решение

GitHub Releases не создаём, пока в репозитории нет воркфлоу по тегу, который собирает архив, SBOM и
контрольные суммы и прикладывает их к релизу. До этого момента:

- единица поставки — **тег**; архив собирается по `git ls-files` (это воспроизводимо: один и тот же
  набор файлов, `zip -X` без лишних метаданных);
- README описывает доставку как «скачайте папку проекта целиком (или клонируйте репозиторий)»;
- страницу тега GitHub использует сам — для истории версий этого достаточно.

Граница применимости: решение перестаёт действовать в тот момент, когда появляется CI-сборка
вложений (пункт 20 плана, `tools/release.py` плюс job по тегу). Тогда релиз создаётся автоматически
вместе с файлами, и первым же таким релизом закрывается пункт 1 плана — «в Releases лежит архив
последней версии».

## Последствия

- Раздел Releases остаётся пустым — это осознанное состояние, а не недоделка; в CHANGELOG и
  IMPROVEMENT-PLAN сказано, при каком условии оно изменится.
- Описание релиза больше не может обещать файлов, которых нет: релиз создаётся только тем
  воркфлоу, который эти файлы и прикладывает.
- Откат дешёвый в обе стороны: `gh release delete <tag> --yes` убирает релиз, не трогая тег;
  `gh release create <tag>` возвращает страницу. Проверено на 1.23.2 и 1.23.3 — теги остались на
  месте, история версий не пострадала.
- Уточнение [ADR-0047](0047-exe-release-checksums.md): вложения может собрать и локальный
  `build_exe.bat`, а приложить их к релизу — сопровождающий вручную; CI-сборка остаётся
  предпочтительной, но перестаёт быть обязательным условием.
- Затронуты: `docs/adr/0046-releases-with-assets-only.md`, `docs/IMPROVEMENT-PLAN.md`
  (пункты 1 и 20 читаются с этой поправкой), `CHANGELOG.md`, `README.md` (версия).
