# ADR-0035. Поиск по мере набора: частичные слова, порядок и один движок на две вкладки

- Статус: принято
- Дата: 2026-11-19
- Владелец: @Ven4esters
- Пересмотр: 2027-11-19
- Версия: 1.13.0

## Контекст

Поиск и так срабатывал на каждый символ (`textChanged` → перестроение списка), но
находил не всё: набрав `Mar`, человек не видел «Стену March». Причина — словарь лемм
(ADR-0033): английское `March` имеет лемму `март`, и в индексе оставалась только она.
Совпадение по началу слова (`mar`) с кириллической леммой невозможно.

Кроме того, список шёл в порядке библиотеки: при запросе `March` строка «Стена March»
могла стоять ниже случайных совпадений, а «чем точнее запрос — тем понятнее порядок»
не выполнялось.

Третья проблема — дублирование: на вкладке «Размеры» логика поиска жила внутри виджета,
и такую же понадобилось сделать в выборе предмета на вкладке «Навигация».

## Решение

### 1. В основах слова хранится само слово

`LemmaBook.stems()` теперь возвращает **само слово** вместе с леммой и связками:
`March` → `march, март`. Слово в наборе обязательно, иначе поиск по первым буквам
английских названий ломается. Лемма и связки остаются — они отвечают за падежи и
двуязычность.

### 2. Три ступени совпадения вместо одной

`NameSearch.match()` (работает на каждое нажатие клавиши):

1. **точная** ступень — слова и номера как записаны (`Стена 01` находит `01-10`);
2. если пусто — **без учёта нулей**: `Стена 1` находит `01-39` (ADR-0031);
3. если пусто — **по началу номера**: `Стена 0` находит `01-39`, пока номер не дописан.

Ступени включаются только когда предыдущая не дала ни одной строки, поэтому точная запись
всегда в приоритете: `Стена 1` при наличии `1-10` не подмешивает `01-10`.

### 3. Порядок по точности

`SearchIndex.score()`: точное слово или лемма — 3, начало слова — 2, часть слова — 1.
Сортировка: точнее выше; при равенстве — короче название (в нём меньше лишних слов);
дальше — порядок библиотеки. Набор `M` → `Ma` → `Mar` → `March` только сужает выдачу:
совпадение по подстроке монотонно, поэтому «чем точнее запрос, тем меньше вариантов»
выполняется по построению.

### 4. Один движок на две вкладки

`NameSearch` — небольшой класс в `domain/search.py`: кэш разобранных названий (`reset()`
после изменения библиотеки), флаг `note` («без учёта нулей» / «по началу») для подсказки и
`match(names, query)`. Им пользуются и вкладка «Размеры», и выбор предмета на вкладке
«Навигация» — правила поиска обязаны совпадать, и теперь они заданы в одном месте.

Вкладка «Навигация» показывает над строкой «Предмет» то же поле поиска и подсказку
«Найдено: N из M». Выбранный предмет остаётся в списке, даже если не подошёл под запрос:
иначе фильтр молча снимал бы выбор.

## Последствия

- `Mar` находит «Стену March», `Mar TID` — только её.
- Порядок предсказуем: сначала точные совпадения, потом частичные.
- Обе вкладки ищут одинаково; расхождение между ними теперь невозможно без изменения
  `NameSearch`.
- Число строк при наборе не растёт: третья ступень срабатывает только на пустой выдаче.
- Тесты: `tests/test_search.py` (набор по буквам, сужение, порядок, три ступени номеров,
  кэш и сброс) и `tests/test_ui.py` (поиск на обеих вкладках, выбор из отфильтрованного
  списка, сохранение выбранного предмета).

## Альтернативы

- **Искать только по леммам, добавив в словарь английские префиксы.** Пришлось бы
  перечислять все начала слов — то есть отказаться от поиска по мере набора.
- **Fuzzy-поиск (расстояние Левенштейна).** На каждое нажатие и 200 строк — дорого и
  шумно; при этом падежи и опечатки уже закрыты словарём.
- **Отдельная копия логики на каждой вкладке.** Две реализации неизбежно разойдутся
  в правилах диапазонов и нулей.
