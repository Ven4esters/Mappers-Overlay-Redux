# ADR-0031. Правила поиска по библиотеке размеров

- Статус: принято
- Дата: 2026-11-19
- Владелец: @Ven4esters
- Пересмотр: 2027-11-19
- Версия: 1.10.3, уточнено в 1.10.4, 1.11.0 и 1.13.0

## Контекст

Заказчик пишет названия «пачкой» и просит, чтобы поиск это понимал:

```
Стена March, TID, Hood, Soup, New, 01-39
```

- находить по любому слову и их комбинации: «Стена», «Стена March», «Стена TID»,
  «Стена March \*» (звёздочка = «дальше любое»);
- находить по номеру из диапазона: «Стена 01», «Стена 05», «Стена 10»;
- число через дефис — диапазон, причём `01-10`, `001-10` и `1-10` — **разные** диапазоны;
- у стен есть варианты, записанные отдельными предметами: «Длинная стена …», «Стена с
  дверным проёмом …», «Полустена …», «четверть стены …». Они должны находиться по общим
  словам («стена»), хотя это другие записи.

Причина такой записи простая: у всех этих стен одинаковые габариты (2.9 × 2.7 м), поэтому
в библиотеке они отличаются только названием, и искать их нужно одним запросом.

До 1.10.3 поиск был подстрокой по всему названию: «Стена 05» не находило ничего
(`05` в тексте `01-39` нет), а «Стена» не находило «четверть стены» (там `стены`).

## Решение

`map_overlay/domain/search.py`: название разбирается на **синонимы**, у слов сравниваются
**основы**, а номера — **точно**.

### 1. Синонимы через запятую (и точку с запятой)

Название режется по `,` и `;`. Каждый фрагмент — отдельный синоним, каждое слово фрагмента —
отдельное слово поиска. Поэтому «Стена TID» находит запись, где `Стена` и `TID` стоят в
разных фрагментах, и порядок слов не важен.

### 2. Диапазон номеров

Если фрагмент заканчивается на «число-число», он разворачивается:

| В названии | Номера поиска |
| --- | --- |
| `01-39` | `01, 02, …, 39` |
| `001-10` | `001, 002, …, 010` |
| `1-10` | `1, 2, …, 10` |

Ширина берётся из **первого** числа, поэтому `01-10`, `001-10` и `1-10` — разные диапазоны.
Номер из запроса сравнивается с номером названия **точно**: «Стена 01» найдёт `01-39`
и не найдёт `001-10` или `1-10`. Это прямое требование заказчика.

Диапазон разворачивается и внутри синонима (`Стена 05-07, склад` → «Стена 05»… «Стена 07»),
и в любом количестве (`Стена 01-03, 10-12`). Обратный диапазон (`39-01`) разворачивается
как прямой. Слишком длинный (больше 1000 номеров) не разворачивается вовсе: это опечатка,
и запись остаётся искать только по тексту.

### 3. Основы слов вместо точного совпадения

С 1.11.0 основы берутся из словаря лемм (ADR-0033): у слова есть своя лемма и связки с
другими языками (`стен ↔ wall`). Для слов вне словаря работает прежнее отбрасывание
окончаний (`-а`, `-ы`, `-ой`, `-ая`, `-ом`, `-ами`…, список в `_ENDINGS`). Поэтому одним
запросом «стена» находятся:

- «Стена March, …»;
- «Длинная стена …»;
- «Стена с дверным проёмом …»;
- «Полустена …» (в основе `полустен` есть `стен`);
- «четверть стены …» (`стены` → `стен`).

Основа ищется как подстрока, поэтому «стен», «ящ», «палл» тоже работают. Цена — возможные
лишние совпадения по коротким основам («стол» найдёт «столб»): для библиотеки на 200
строк это приемлемо, зато падежи и составные слова больше не мешают.

### 4. Звёздочка

`*` в запросе означает «дальше любое» и просто игнорируется: «Стена March \*» = «Стена
March». Так запросы, скопированные из документации, работают как ожидается.

### 5. Пустой запрос

Пустая строка (или одни звёздочки) показывает всю библиотеку.

## Уточнение 1.10.4: запасное сравнение без учёта нулей

Строгое правило про ширину чисел оказалось слишком строгим на практике: человек,
который помнит предмет как «Стена 1», не находил запись `01-39` и решал, что поиск
сломан. Решение — два прохода:

1. **точный** проход: номер сравнивается с номерами названия как записан (`01` ≠ `1`);
2. если точный проход не дал **ни одной** строки и в запросе есть число — **запасной**
   проход сравнивает номера по значению (`1` = `01`).

Точная запись всегда в приоритете: при записях `01-10` и `1-10` запрос «Стена 01» покажет
только `01-10` и не подмешает `1-10`. Запасной проход включается лишь когда иначе было бы
пусто, и подсказка об этом честно пишет: «Найдено: 1 из 6 · номер совпал без учёта нулей».

Реализация: `SearchIndex.matches(words, ignore_padding=True)`, поле `values` с номерами
по значению. Решение принимается на уровне списка (`SizesTab._visible_items`), потому что
зависит от всей библиотеки, а не от одной записи.

## Уточнение 1.13.0: набор по буквам и порядок выдачи

Поиск работает на каждый символ, поэтому слово в индексе хранится и **как записано**, а не
только леммой: `Mar` находит `March`. Номера получили третью, самую запасную ступень —
совпадение по началу (`Стена 0` → `01-39`), пока номер не дописан. Строки идут по точности:
точное слово, начало слова, часть слова; при равенстве — короче название. Подробности и
мотивы — ADR-0035.

## Последствия

- Поиск стал предсказуемым для «пачечных» названий; библиотеку можно вести без
  дублирования размеров.
- Номер из запроса — это номер из диапазона, а не подстрока: «Стена 1» и «Стена 01»
  находят разные записи. Это записанное требование, а не ошибка.
- Основы неполные (без словаря): «стен» найдёт и «стенд». При необходимости список
  окончаний расширяется в одном месте — `_ENDINGS`.
- Разбор названия кэшируется на вкладке «Размеры» до изменения библиотеки, поэтому
  расширение диапазонов не тормозит ввод.
- Индекс не меняет формат `config/sizes.json`: всё вычисляется из названия.
- Тесты: `tests/test_search.py` (47 проверок: диапазоны, ширина чисел, основы, варианты,
  звёздочки) и сквозные проверки в `tests/test_ui.py`.

## Альтернативы

- **Хранить диапазон отдельным полем.** Пришлось бы менять схему файла и объяснять
  заказчику новую форму; в названии диапазон уже есть и читается человеком.
- **Регулярка по всему названию при каждом вводе.** Не даёт сравнения основ: «стена» и
  «стены» остаются разными словами.
- **Полный морфологический анализ (pymorphy).** Лишняя зависимость на 30 МБ ради поиска
  по 200 строкам; отбрасывания окончаний достаточно.
