Всё, что ниже, должно быть зафиксировано в CONTRIBUTING.md, STYLEGUIDE.md, настройках CI и шаблоне PR.

## 1. Базовые принципы чистоты кода

- Читаемость важнее «умности»: код пишется для людей, компилятор/интерпретатор — вторичен.
- KISS, DRY, YAGNI, SOLID — как ориентиры, не как религия. Не создавайте абстракцию «на будущее».
- Явное лучше неявного: зависимости, побочные эффекты, ошибки, контракты — явно.
- Одна ответственность: модуль/класс/функция решают одну задачу.
- Маленькие функции и блоки: ориентир — до 30–40 строк и до 3–4 уровней вложенности; если больше — декомпозируйте.
- Низкая цикломатическая сложность: ориентир ≤ 10–15 на функцию; выше — рефакторинг или обоснование.
- Никакого мёртвого и закомментированного кода, «временных» флагов и TODO без тикета.
- Магические числа и строки — в константы/конфиг с понятными именами.
- Неизменяемость по умолчанию, где это уместно; минимум глобального состояния.
- Явная обработка ошибок, никаких «проглоченных» исключений.
- Границы приложения валидируют вход: не доверяйте пользователю, сети, БД, внешним API.

## 2. Стиль и форматирование

- Единый formatter и linter в CI: например, Prettier/ESLint, Black/Ruff/mypy, gofmt/golangci-lint, rustfmt/clippy, PHP-CS-Fixer/PHPStan, Checkstyle/SpotBugs.
- Автоформатирование обязательно; споры о стиле решает инструмент, а не ревьюер.
- Правила именования:
  - классы/типы — PascalCase;
  - функции/переменные — camelCase или snake_case по языку;
  - константы — UPPER_SNAKE_CASE;
  - булевы — is/has/can/should;
  - без сокращений, кроме общепринятых (id, url, http).
- Файлы и пакеты — по смыслу, не utils2, common, misc.
- Длина строки — по языку/линтеру (обычно 80–120).
- Импорты отсортированы, неиспользуемые удалены.
- Публичные API имеют явные типы/контракты, где язык это позволяет.

## 3. Архитектура и структура

- Чёткое разделение слоёв: представление/API, бизнес-логика, доступ к данным, инфраструктура.
- Бизнес-логика не зависит от фреймворка, БД и UI.
- Зависимости внедряются явно; никаких скрытых синглтонов и «сервис-локаторов».
- Публичные контракты модулей стабильны; внутренние детали не протекают наружу.
- Конфигурация — через переменные окружения/конфиг-файлы, не хардкод.
- Для значимых решений — ADR (Architecture Decision Record): контекст, решение, последствия.
- Обратная совместимость API и схем БД — осознанно; версионирование по SemVer.

## 4. Документация и комментарии

- README: назначение, запуск, тесты, конфигурация, деплой.
- Публичные функции/классы/модули — docstring/JavaDoc/KDoc с параметрами, возвратом, ошибками.
- Комментарии объясняют почему, а не что; код должен говорить сам за себя.
- Для API — OpenAPI/AsyncAPI/GraphQL-схема и примеры.
- Для БД — миграции и описание схемы.
- CHANGELOG для пользовательских изменений.
- TODO/FIXME — только с тикетом и владельцем.

## 5. Обработка ошибок и логирование

- Единая модель ошибок: коды/типы, сообщения, причины, контекст.
- Не логируйте и не возвращайте секреты, токены, пароли, PII.
- Логи — структурированные (JSON), с уровнями DEBUG/INFO/WARN/ERROR, correlation/request ID.
- Ошибки не глотать; добавлять контекст при пробросе.
- Различайте ожидаемые бизнес-ошибки и технические сбои.
- Fail fast на старте: проверка конфигурации, зависимостей, миграций.
- Ретраи — только идемпотентные, с backoff и лимитом; таймауты обязательны для всех внешних вызовов.
- Не логируйте в цикле «на каждый чих»; не используйте print/console.log в проде.

## 6. Безопасность — обязательный минимум

- Валидация и нормализация входа на границе; выход — экранирование/кодирование по контексту.
- Параметризованные запросы; никакой конкатенации SQL.
- Аутентификация и авторизация на каждом чувствительном действии (не только на UI).
- Пароли — только стойкие хеши (Argon2id/bcrypt/scrypt), не MD5/SHA1.
- Секреты — в vault/секрет-хранилище, не в репозитории; сканирование секретов в CI.
- TLS везде; безопасные заголовки; CORS минимально необходим.
- Принцип наименьших привилегий для сервисов, БД, токенов.
- Зависимости сканируются на уязвимости (SCA); критические — блокируют релиз.
- OWASP Top 10 — обязательный чек-лист для веб/API.
- Логи и ошибки не раскрывают внутреннюю структуру атакующему.

## 7. Тестирование — что обязательно

- Пирамида тестов: много unit, меньше integration, минимум e2e.
- Unit-тесты детерминированы, быстрые, без сети/БД/времени/рандома без контроля.
- Integration-тесты проверяют БД, очереди, внешние адаптеры (контрактно/через testcontainers).
- E2E — только критические пользовательские сценарии.
- Обязательные кейсы: happy path, границы, негативные сценарии, ошибки зависимостей, конкурентность/идемпотентность, права доступа.
- Регрессионный тест на каждый исправленный баг.
- Контрактные тесты для API/событий.
- Покрытие — индикатор, не цель: критичные модули и бизнес-правила должны быть покрыты; 80% — разумный ориентир, но не догма.
- Тесты — часть кода: читаемые, с понятными именами, без дублирования логики продакшена.
- Flaky-тесты чинятся или удаляются; «зелёный CI» не должен быть случайным.

## 8. Обязательные проверки в CI (quality gates)

PR не мержится, если не прошли:

- Форматирование.
- Линтер.
- Проверка типов (если есть).
- Unit- и integration-тесты.
- Сборка артефакта.
- SAST (статический анализ безопасности).
- SCA — сканирование зависимостей.
- Secret scanning.
- Проверка миграций БД (вперёд/назад, отсутствие destructive без плана).
- Контрактные тесты/OpenAPI-валидация.
- Сканирование контейнера (если есть).
- Проверка лицензий зависимостей.
- Минимум одно одобрение ревьюера; для критичных модулей — два.
- Заполненный шаблон PR: что, зачем, как тестировалось, риски, откат.

## 9. Code Review — обязательные детали

- PR маленькие: ориентир до 300–400 строк изменений; большие — дробить.
- Ревьюер проверяет: корректность, читаемость, тесты, безопасность, обработку ошибок, обратную совместимость, производительность, документацию.
- Автор отвечает на все комментарии; спорные решения — в тикет/ADR.
- Не мержить с «красным» CI, конфликтами, незакрытыми блокирующими комментариями.
- Запрещён self-merge без политики исключений.
- Никаких force-push в общие ветки; история должна быть понятной.
- Коммиты — Conventional Commits или принятый стандарт; сообщение объясняет смысл.
- Ветки — по тикету; защита main/release-веток.

## 10. Зависимости и конфигурация

- Минимум зависимостей; каждая новая — с обоснованием.
- Фиксация версий lock-файлом; обновления — регулярно и через CI.
- Лицензии проверяются; запрещённые — блокируют.
- Конфиг валидируется на старте; секреты не попадают в образы и логи.
- Feature flags — с владельцем и сроком жизни; удаляются после раскатки.

## 11. API, БД, конкурентность

- API: версионирование, предсказуемые ошибки, пагинация, идемпотентность, таймауты, лимиты.
- БД: миграции только через инструмент, обратно совместимые; индексы под запросы; N+1 проверяется.
- Транзакции — осознанно; уровни изоляции понятны.
- Конкурентность: блокировки, идемпотентность, retry, dead-letter для очередей.
- Внешние вызовы — с таймаутами, circuit breaker, backoff.

## 12. Наблюдаемость и эксплуатация

- Структурные логи, метрики, трассировки; correlation ID сквозь сервисы.
- Health/readiness endpoints.
- Алерты на симптомы для пользователя, а не на каждый чих.
- Runbook для критичных сервисов; план отката.
- Никаких PII/секретов в логах и метриках.

## 13. Definition of Done — обязательный минимум

Задача считается выполненной, только если:

- код соответствует стайлгайду и прошёл линтеры/форматтеры;
- есть тесты на новое поведение и регрессию;
- CI зелёный, quality gates пройдены;
- ревью выполнено;
- документация/CHANGELOG обновлены, если нужно;
- миграции и конфиг проверены;
- нет новых критичных уязвимостей и секретов;
- понятен план отката/включения фичи;
- выполнены нефункциональные требования: производительность, безопасность, доступность.

## 14. Что зафиксировать в команде

- Языковые стандарты: PEP 8 + Ruff/mypy, Google Java Style + Checkstyle, Effective Go + golangci-lint, Airbnb/ESLint + Prettier, PSR-12 + PHPStan, rustfmt + clippy.
- Политику веток, PR и релизов.
- Порог покрытия и список критичных модулей.
- Уровни логирования и правила работы с PII.
- Обязательные CI-джобы и правила блокировки мержа.
- Шаблон PR, issue, ADR, bug report.
- Политику зависимостей и обновлений безопасности.

Главное: стандарты должны быть автоматизированы, а не существовать только в вики. Если правило нельзя проверить линтером, тестом или CI — оно будет нарушаться.
