# Как контрибьютить

Документ фиксирует правила, которые проверяются автоматически. Если правило нельзя
проверить линтером, тестом или CI — оно не работает.

## Перед правкой

Прочитайте `docs/LESSONS.md` — памятку по ошибкам и их решениям. Там зафиксировано, что
считать эталонным поведением (первая версия 2.0, коммит `d2db3d0`), какие умолчания нельзя
менять без теста и как проверять выпуск.

## Ветки и коммиты

- Ветка — от актуального `main`, имя по смыслу: `feature/movement-diagonals`,
  `fix/paste-verification`. Ветки `utils2`, `new`, `temp` запрещены.
- Коммиты — [Conventional Commits](https://www.conventionalcommits.org/):
  `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `build:`, `chore:`.
  Сообщение объясняет **смысл**, а не перечисляет файлы.
- Force-push в общие ветки запрещён. `main` защищён: только через PR.

## Pull request

- Размер — до 300–400 строк изменений. Больше — дробить.
- Заполняется шаблон `.github/pull_request_template.md`: что, зачем, как проверялось,
  риски, план отката.
- Нужно минимум одно одобрение; для `lsp_overlay/domain/` и `lsp_overlay/application/` — два.
- Мержить «красный» PR нельзя. Конфликты и незакрытые блокирующие замечания — тоже.

## Definition of Done

Задача закрыта, когда:

1. код проходит `ruff check`, `ruff format --check`, `mypy`;
2. тесты зелёные, покрытие не ниже 80 %;
3. на новое поведение есть тест, на исправленный баг — регрессионный;
4. обновлены `README.md`/`CHANGELOG.md`, если изменилось поведение;
5. нет секретов, отладочных `print` и закомментированного кода;
6. понятно, как откатить изменение.

## CI (quality gates)

`.github/workflows/ci.yml` прогоняет на каждый PR и push в `main`:

| Проверка | Команда |
| --- | --- |
| Форматирование | `ruff format --check .` |
| Линтер | `ruff check .` |
| Типы | `mypy lsp_overlay` |
| Тесты + покрытие | `pytest --cov=lsp_overlay --cov-fail-under=80` |

Если добавлены новые зависимости — обновите `requirements*.txt` и объясните причину в PR.

## Тесты

- Пирамида: много unit (ядро), меньше интеграционных (сессия + панель), немного дымовых
  тестов UI в offscreen-режиме.
- Тесты детерминированы: без сети, без реального времени (паузы передаются как `sleep`),
  без рандома без seed.
- Обязательные кейсы: happy path, границы, негативные сценарии, отказ зависимостей.
- Flaky-тест чинится или удаляется: «зелёный CI» не должен быть случайным.

## Ошибки и логи

- Ожидаемые сбои — наследники `DomainError` (например, `JumpTooLargeError`, `ApplyError`).
  Технические — обычные исключения, которые пробрасываются с контекстом.
- `print` в коде приложения запрещён: только `logging`. Логи — JSON-строки в `logs/overlay.log`.
- В логи не попадают секреты и персональные данные. Их у приложения нет — так и держим.

## Безопасность

- Ввод с клавиатуры и мыши — единственное «внешнее воздействие» приложения; никаких сетевых
  вызовов, никакой работы с памятью игры.
- Секреты в репозиторий не коммитятся; при появлении — CI-джоба secret scanning.
- Зависимости ставятся с фиксированными версиями-минимумами; новые — только с обоснованием.

## Документация

- Публичные функции и классы — docstring с параметрами и ошибками.
- Комментарии объясняют **почему**, а не что.
- Значимые решения — ADR в `docs/adr/` (контекст, решение, последствия).
- `TODO`/`FIXME` — только с номером задачи.
